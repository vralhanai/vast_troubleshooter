# Vast Troubleshooter design review

Reviewed `README.md` and `PLAN.md` on 2026-11-23. I used `STEPS.md`, `pyproject.toml`, and the CLI stub to check how the design would translate into implementation. This is a design review. The repository has a placeholder CLI, and no behavior was validated on an Ubuntu rental host. The public host setup console did not expose its guide in the retrieved page. [Vast host setup console](https://cloud.vast.ai/host/setup/)

**Recommendation.** Proceed with the read-only diagnostic POC and demonstrate repair on a disposable Ubuntu VM. Live-host repair needs a reliable way to establish rental state and prevent a new assignment during the repair. Define the privilege boundary and safe output schema before building collectors that touch Docker, privileged logs, or rental metadata. The existing dry-run default, named fixes, and partial results are worth keeping.

## Security and customer safety

### 1. Blocker — Rental safety needs an enforceable precondition

`README.md` §6 item 2 allows the operator to confirm disruption during a rental. Its decisions table says disruptive actions are blocked. `PLAN.md` §§1.7 and 1.9 check rental state before the confirmation prompt, and the POC uses a running test container as its acceptance case. An empty container list cannot establish that the host is safe to repair. Vast documents both Docker and VM rentals, and stopped or transitional workloads can still belong to a customer. Stale logs, a stopped daemon, an unreadable source, or a query aimed at the wrong engine can also produce an apparently empty result. [Vast machine metrics](https://docs.vast.ai/host/machine-metrics) · [Vast offline troubleshooting](https://docs.vast.ai/host/machine-offline)

- Define `active`, `none`, and `unknown` against validated sources that cover VM and container backends, allocated-but-stopped workloads, and assignment transitions. Require fresh and complete evidence for `none`. Treat missing, stale, conflicting, or unsupported evidence as `unknown`. Both `active` and `unknown` must block disruptive apply, including when the operator confirms.
- Acquire or verify a maintenance state that prevents new assignments throughout the operation, then recheck evidence after confirmation and immediately before mutation. A host-local lock can serialize this tool's own invocations. It cannot prevent the platform from assigning a new workload. Vast's driver guidance explicitly says a scheduled maintenance window alone neither unlists the host nor clears instances. If the no-API design cannot verify the required state, keep disruptive fixes advisory on production hosts. [Vast driver maintenance guidance](https://docs.vast.ai/host/upgrade-nvidia-driver)
- Add acceptance cases for VM-only activity, stopped but allocated workloads, permission failure, stale or conflicting sources, a state change at confirmation, and concurrent fix invocations. A test container can demonstrate the stop condition in a lab. Production readiness requires validating coverage on a representative host.

### 2. Blocker — Treat Docker access and elevation as security boundaries

`README.md` §6 items 7–8 and `PLAN.md` §1.9 rely on command allowlists and Unix privilege tiers. Access to a rootful Docker socket carries root-level authority, even when the collector requests only `docker info`. A read-only bind mount of the socket does not restrict Docker API methods. Inherited Docker contexts and environment settings can also point the tool at another host, undermining both the diagnosis and rental checks. `STEPS.md` steps 3 and 12 need a single, explicit policy for privilege and how the command runner selects targets. [Docker Engine security](https://docs.docker.com/engine/security/) · [Docker group privileges](https://docs.docker.com/engine/install/linux-postinstall/) · [Docker daemon endpoints](https://docs.docker.com/reference/cli/dockerd/)

- Run parsing, rules, rendering, and ordinary collectors as the invoking user. If elevated operations are needed, use a narrow system-owned launcher or helper exposing fixed operations. Keep its executables, imports, and policy out of user-writable checkouts, virtual environments, and configuration. Bind each operation to an approved executable, argument schema, minimal environment, and trusted local endpoint. Reject unsupported or ambiguous endpoints and avoid granting persistent Docker access for diagnostics.
- Use separate allowlists for reads and mutations. Validate dynamic operands such as block-device identifiers against trusted enumeration. Disable implicit pager and interactive behavior for privileged reads, drain bounded output, and define timeout and child cleanup behavior. Test refusal of unexpected operands, inherited environment overrides, remote daemon selection, and denied permissions.
- Make the Windows dev container fixture-first and non-root. Specify that the default has no host Docker socket, host filesystem or log mounts, host namespaces, or elevated capabilities. Allow optional GPU passthrough for the supported WSL 2 configuration and label those facts as container/WSL observations. Bare-metal PCIe, systemd, kernel, and rental behavior need Ubuntu host coverage. [Docker Desktop GPU support](https://docs.docker.com/desktop/features/gpu/)

### 3. Blocker — Build shareable output from allowlisted fields

`README.md` §6 promises redaction and no customer data. `PLAN.md` §§1.6–1.7 put `raw_excerpt`, `source_command`, all facts, and action logs on the path to export. `STEPS.md` retains matching kernel and daemon lines and postpones redaction until step 16, after diagnostic JSON and action logging. Metadata and logs can contain identifiers, labels, paths, command arguments, signed URLs, credentials, and tenant content. Pattern matching can miss arbitrary text and multiline secrets. Vast itself asks hosts to scrub sensitive material before sending logs. [Vast support guidance](https://docs.vast.ai/host/machine-offline#4-contact-vast-ai-support)

- Collect the minimum data needed and extract bounded, typed evidence such as an Xid code, service state, or aggregate count. Keep container and VM observations to the fields needed for rental state. Prefer selected systemd properties over status output with process command lines and journal excerpts. Never access customer files, container environment variables, command lines, or workload logs for the POC.
- Define the shareable schema before wiring collectors to CLI output. Allowlist its fields and apply one safe rendering path to terminal, JSON, Markdown, exceptions, and action summaries. Escape terminal controls and Rich markup, and render Markdown evidence as inert text. Use redaction as a second layer. Remove `--no-redact` from the shareable report contract and let the operator preview the exact files before attaching them. Keep any separately requested support routing identifier explicit.
- Write reports and backups with restrictive permissions at creation. Keep report paths on the unprivileged side, use safe file creation, and handle symlinks and collisions explicitly. Record fix ID, timestamps, phase, and sanitized outcomes in action logs. Define retention and test that seeded secrets and customer identifiers stay out of every output, including error paths and committed fixtures. Cover IPv6, multiline secrets, nested data, and malicious control characters.

### 4. High — Define per-fix recovery and remote-access preconditions

`PLAN.md` §§1.6–1.7 model a fix with a privilege flag, rental flag, dry run, and undo notes. `STEPS.md` step 15 proposes restarting the Vast daemon and replacing the resolver with a public resolver. A DNS failure can reflect a VPN, split DNS, an upstream outage, or a managed configuration. Replacing the resolver can break name resolution or leak internal queries. A restart can fail partway and leave an already degraded host unreachable.

- For the VM demo, restore a known-good configuration through the resolver manager that owns it. Capture the expected pre-change state, verify that it still matches after confirmation, and require an independent recovery path for network changes. If live repair is eventually supported, validate systemd-resolved, Netplan, DHCP and static-file cases separately. Keep unsupported or ambiguous cases advisory.
- Specify the target, expected change, failure behavior, and postconditions for every fix. Handle timeouts with an observed final state or an explicit indeterminate outcome. Preserve owner, mode and prior configuration for reversible file changes, verify rollback, and test repeat invocation and concurrent configuration changes. For a daemon restart, document recovery and verify stable service health. An interrupted workload cannot be restored by undoing a restart.
- Keep controller reset, driver/kernel changes, SSH reconfiguration, firewall changes, and Secure Boot changes out of POC apply. The controller-reset summary in the Verified requirements section of `PLAN.md` omits the vendor script that resends machine information. Carrying out the vendor procedure would affect controller state and trigger network reporting, so keep it as a link to the vendor runbook for operator-led maintenance. [Vast offline troubleshooting](https://docs.vast.ai/host/machine-offline#3-reset-the-controller-connection-and-restart-vastai)

### 5. High — Separate passive diagnosis from outbound and load-generating probes

`README.md` §§3 and 6 describe offline and read-only behavior while `PLAN.md` §§1.3–1.5 include external connections, speed tests, and Docker GPU test runs. Even a simple DNS or TCP probe can expose the host's egress address and timing. Starting a container changes daemon state and consumes resources. Speed tests, GPU workloads, and SSD self-tests can compete with rentals. `STEPS.md` already defers some of these operations. Carry that distinction into the user-facing contract. [Vast offline network checks](https://docs.vast.ai/host/machine-offline) · [Vast SSD health guidance](https://docs.vast.ai/host/ssd-health)

- Provide a local-only mode with zero outbound probes and make it the default for support report generation. Put outbound probes behind an explicit choice, list destinations and data exposed, and bound DNS time, connections, concurrency, bytes, and redirects. Use owned or documented endpoints, verify TLS where applicable, and send no credentials or raw evidence. A TCP connection to a public resolver is a destination-specific observation, with limited value as a general health signal.
- Keep speed tests, device self-tests, and GPU container runs out of default diagnostics. For a future opt-in GPU test, require a verified idle maintenance state, a reviewed image pinned by digest, explicit pull consent, bounded resources, cleanup, and no customer mounts. Treat local listening sockets and configured port ranges as local evidence. WAN reachability requires a separate external observation against operator-authorized targets and ports.

### 6. High — Make security recommendations evidence-based

`PLAN.md` §§1.5 and 1.8 propose a kernel vulnerability check and pair Secure Boot with SSH password login. They carry different risks. Report the platform's Secure Boot requirement and the boot-integrity trade-off separately. For SSH, evaluate effective policy for the relevant connection contexts, including drop-ins, `Match` blocks and keyboard-interactive authentication. Avoid reading private keys or inferring fleet-wide key reuse from a single host. Keep both checks advisory and reference the vendor's separate-login and recovery guidance. [Vast verification requirements](https://docs.vast.ai/host/verification-stages) · [Vast SSH guidance](https://docs.vast.ai/host/disable-ssh-password-login)

For kernel patch status, evaluate the running image and Ubuntu package build against release-, architecture-, and flavor-specific vendor data. Distinguish a patch installed but awaiting reboot from a running patched kernel. If the tool ships offline advisory data, record its revision and freshness and surface `unknown` for stale snapshots, custom kernels, or unidentified live-patch state. Use Canonical's advisory data for affectedness and a separately sourced exploited status if the tool reports one. A generic comparison of upstream `uname` versions misses distribution backports. [Canonical Ubuntu OVAL](https://documentation.ubuntu.com/security/security-updates/oval/) · [Vast kernel upgrade guidance](https://docs.vast.ai/host/upgrade-kernel)

### 7. High — Protect the fix catalogue and release chain

`README.md` §6 item 10 covers dependency pinning and checksums. `PLAN.md` §§1.4 and 1.13 leave command authority in the fix catalogue ambiguous. Use bundled, versioned rules with a closed schema, bounded size and depth, and a restricted comparison language. Let rules reference compiled fix IDs. Keep command templates, risk classification, rental gates, and elevation policy in reviewed code and outside any user-editable rule data. Rule data, findings and imported reports should be unable to supply privileged paths, arguments, or a pre-approved action.

Use a committed lockfile and frozen CI installs, verify the package built from a clean checkout, and pin the container base image digest with an update cadence. Scan runtime, build and image dependencies and document how security fixes reach users. Public releases should have verifiable provenance or signatures in addition to checksums. If a privileged helper is introduced, test that its installation and update path preserve system ownership.

## Diagnostic accuracy and delivery

### 8. High — Correct the source-backed NVIDIA requirements

`README.md` §4 and `PLAN.md` §§1.8, 1.15 and Verified requirements repeat that Vast publishes no numeric NVIDIA driver minimum. The linked **Upgrade the NVIDIA Driver** page publishes a table. At review time it lists `595.91.07` for Turing and newer already on `595.xx`, `610.57.04` for other applicable branches on Turing and newer, and `580.178.04` for Maxwell, Pascal and Volta. The guide handles newer unlisted branches separately. Capture the dated source and branch conditions, define how unknown or unlisted combinations are shown, and test the boundaries. Keep the POC finding advisory. [Vast driver upgrade table](https://docs.vast.ai/host/upgrade-nvidia-driver)

`nvidia-smi` reports driver-supported CUDA capability. Keep that fact distinct from installed toolkit version and container runtime health. Apply the documented ARM64 CUDA threshold and architecture caveat. Vast's CPU table lists both ARM64 and AVX without resolving their applicability. Clarify that before coding a universal AVX check. Use separate rule types or metadata for verification baselines, self-test rules, and documented causes of de-verification. Also correct the README's blanket association between “unverified” and being de-listed. Vast distinguishes newly evaluated machines from previously verified machines that appear as unverified. [NVIDIA SMI field definitions](https://docs.nvidia.com/deploy/nvidia-smi/index.html) · [Vast verification stages](https://docs.vast.ai/host/verification-stages) · [Vast self-test guidance](https://docs.vast.ai/host/how-to-self-test) · [Understanding Verification](https://docs.vast.ai/host/understanding-verification)

### 9. Medium — Preserve uncertainty from collection to CLI output

`PLAN.md` §§1.6, 1.8, and 1.11 describe error facts but leave rule matching and overall outcome unclear. Define `pass`, `fail`, `unknown`, and `skipped` at the check level, then specify how unknown inputs propagate through rules and influence exit codes. A missing critical collector should produce an incomplete diagnosis even when no rules fired. Distinguish unsupported fields from observed empty values. Document JSON schema versioning, units, evidence timestamps, and rule source/date. State explicitly that the tool estimates local conditions affecting marketplace status. [Understanding Verification](https://docs.vast.ai/host/understanding-verification)

Avoid promoting one symptom to a confirmed cause. A resolver error alone cannot identify the broken component. A generic `nvidia-smi` failure does not establish a library mismatch, and Docker runtime registration alone cannot prove that a GPU workload can launch. Limit log findings by boot or time window and include severity and recurrence. Distinguish negotiated PCIe link estimates from measured throughput, apply the stricter documented `> 2.85 GiB/s` boundary if measuring, and specify storage units and how root and Docker storage are mapped back to physical devices. Add boundary and ambiguous-input fixtures. [Vast offline troubleshooting](https://docs.vast.ai/host/machine-offline) · [Vast verification requirements](https://docs.vast.ai/host/verification-stages) · [Vast SSD health](https://docs.vast.ai/host/ssd-health)

### 10. Medium — Reconcile the POC, implementation sequence, and support matrix

- `PLAN.md` lists the DNS and outbound collector and Windows Docker image in the POC, but its milestone roll-up omits M4 and M8 and includes all of M1/M2, whose disk and PCIe work is listed as deferred. `STEPS.md` adds disk and host-log work before POC verification. Specify the exact collectors and acceptance criteria in one POC scope, then align both milestone lists. If service-down diagnosis is included, make the small systemd state check explicit and defer daemon-log collection.
- Move safe fact schemas and rendering ahead of the first CLI output of collected data, and add the rental and recovery gates before any live-host apply. The POC should pass on a clean Ubuntu VM with a known reproducible fault, a skipped or unavailable check, a successful guarded repair, a blocked repair, a recovery scenario, and a safe report. Windows Docker can verify the fixture-driven CLI contract. Keep host integration tests on Ubuntu.
- `pyproject.toml` and `.python-version` require Python 3.15, while Ubuntu 22.04 and 24.04 ship older defaults. Python 3.15 is released as of this review. If keeping the pin, specify the managed interpreter, its update owner, and locked dependency and wheel availability on each supported architecture. Alternatively, start with one tested Ubuntu release and a supported interpreter available there, then expand after validation. Document the supported Ubuntu, architecture, GPU/driver, and Docker combinations explicitly. [Python release schedule](https://peps.python.org/pep-0790/) · [Ubuntu 22.04 release notes](https://documentation.ubuntu.com/release-notes/22.04/) · [Ubuntu 24.04 release notes](https://documentation.ubuntu.com/release-notes/24.04/)
- Repair the Level 1 decision link in `PLAN.md`. It targets `README.md#8-open-questions`, but the heading is “8. Decisions and open questions.” Update the opening claim that only the support matrix is open to include rental evidence and the first supported repair.
